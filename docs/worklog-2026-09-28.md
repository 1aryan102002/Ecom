## 1. Cart: cart page, update and remove

### What was built

| Piece | File | What it does |
|---|---|---|
| `Cart.__iter__()` | `cart/cart.py` | Lets a template loop over the cart with `{% for item in cart %}`. Each item gets its `Product`, a `quantity_range` for the dropdown, a `Decimal` price and a `total_price`. |
| `Cart.get_total_price()` | `cart/cart.py` | Sum of `price * quantity` for all items. |
| `Cart.update(product_id, quantity)` | `cart/cart.py` | Sets a new quantity for an item that is already in the cart. |
| `Cart.delete(product_id)` | `cart/cart.py` | Removes an item from the cart. |
| `cart_detail` view | `cart/views.py` | `GET /cart/cart-detail/` renders the cart page. |
| `update_cart` view | `cart/views.py` | `POST /cart/update/` → `Cart.update()` → JSON with the new `cart_qty`. |
| `cart_delete` view | `cart/views.py` | `POST /cart/delete/` → `Cart.delete()` → JSON with the new `cart_qty`. |
| URLs | `cart/urls.py` | `cart_detail`, `update_cart`, `cart_delete`. |
| Cart page | `cart/templates/cart/cart_detail.html` | One row per item (image, name, price, quantity dropdown, Update / Remove, item total), grand total, and an empty-cart message. jQuery sends Update / Remove as AJAX POSTs, then reloads the page. |
| Navbar | `MyEcom/templates/MyEcom/base.html` | The cart icon now links to the cart page; the user icon links to the register page. |

`update_cart` and `cart_delete` answer a non-POST request with `405 {"message": "POST required"}`.

### The tricky parts

1. **The session can only store JSON.**
   `request.session` is saved as JSON, so it can hold only `str`, `int`, `list` and `dict`. A `Decimal` or a `Product` object in it crashes the save.
   - The price is stored as `str(product.price)`.
   - `__iter__` works on **copies** of the items (`{pid: dict(item) for ...}`) before adding `Product` and `Decimal` values, so the real session dict is never touched.

2. **Session keys come back as strings.**
   After a round trip through JSON, the dict key `3` becomes `"3"`. Every Cart method does `product_id = str(product_id)` first; otherwise the lookups miss.

3. **`self.session.modified = True`.**
   Django only notices a change when `session["cart"]` itself is assigned. Changing a nested value such as `cart[id]["quantity"]` is invisible to it, so every method that writes sets `modified = True`.

4. **Templates have no `range()`.**
   The quantity dropdown needs the numbers 1 to stock, so `__iter__` adds `quantity_range = range(1, product.stock + 1)` to each item.

5. **One database query instead of one per item.**
   `__iter__` loads every product at once with `Product.objects.filter(id__in=cart.keys())`.

### Behaviour to be aware of

- `Cart.add()` **replaces** the quantity of an item already in the cart; it does not add to it.
- `len(cart)` is the **total quantity** (2 keyboards + 1 mouse = 3), not the number of different products.
- Known gap: if a product is deleted from the database while it is in someone's cart, that item has no `product` key and the cart page will error.

## 2. New `users` app: registration with email verification

### What was built

| Piece | File | Notes |
|---|---|---|
| App registered | `Ecom/settings.py` | `'users'` added to `INSTALLED_APPS`. |
| URLs | `Ecom/urls.py`, `users/urls.py` | Mounted at `/users/`: `register/`, `email-verification/<uidb64>/<token>/`, `email-verification-sent/`, `email-verification-success/`, `email-verification-failed/`. |
| `Profile` model | `users/models.py` | One-to-one with Django's built-in `User` (`user.profile`), holding `phone_number` and `recovery_email`. Registered in the admin. |
| `createuserForm` | `users/forms.py` | Extends `UserCreationForm` with username, email, first/last name, and passwords. Its `save()` also creates the `Profile`. Adds Tailwind classes and placeholders to every field. |
| Token generator | `users/token.py` | `account_activation_token`, built on `PasswordResetTokenGenerator`. The hash uses the user's pk, the timestamp and `is_active`, so the link stops working once the account is activated. |
| `register` view | `users/views.py` | Saves the user, sets `is_active = False`, emails the verification link, then redirects to the "check your email" page. |
| Email backend | `Ecom/settings.py` | `EMAIL_BACKEND = console` – emails are printed in the `runserver` terminal instead of being sent. |
| Templates | `users/templates/users/` | `register.html` plus the five email-verification templates below. |

### The tricky parts

1. **`from six import text_type` failed.**
   `six` was never part of Django or Python; it's a third-party package that helped code run on both Python 2 and 3. Django shipped a copy as `django.utils.six` but removed it in Django 3.0, and old tutorials still use it. On Python 3, `text_type` is just `str`, so `token.py` now uses `str(...)` and needs no extra package.

2. **"Why is `is_active` True when I set it to False?"**
   The first check created a user in the shell with `User.objects.create_user()`. That never runs the `register` view, so it showed Django's default (`True`). Registering through the real view (with Django's test client) gave `is_active = False`, as intended.
   Rule: **only users created through the register page start inactive.** Users created with `createsuperuser`, the admin or the shell start active.

3. **Registration crashed after saving the user.**
   Testing through the real view showed `TemplateDoesNotExist: users/email_verification_email.html`. The user was already saved (inactive) but never got an email, so they could never activate.
   The cause: the templates were created before the views were written, and their names did not match (`Email_Verified.html`, `Email_verification_sent.html`, …). The capital letters also work on Windows but would break on a Linux server.
   The fix: the three old files were deleted and five new ones were created with the exact names the views use:

   | Template | Used by |
   |---|---|
   | `email_verification_email.html` | Text of the verification email (plain text, autoescape off so the link is not mangled) |
   | `email_verification_sent.html` | "Check your email" page shown after registering |
   | `email_verification.html` | Page opened by the link in the email |
   | `email_verification_success.html` | "Email verified" page |
   | `email_verification_failed.html` | "Link invalid or expired" page |

   After the fix, a full registration test passed: 302 redirect to `/users/email-verification-sent/`, user saved with `is_active=False`, email printed in the console with a working link, and all five pages returned 200.

4. **Migrations history.**
   A custom `User` model was created first (`0001_initial`), then deleted (`0002_delete_user`) in favour of a `Profile` linked to Django's own `User` (`0003_initial`). All three migrations are kept because the database has already applied them.
